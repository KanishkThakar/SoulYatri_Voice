# Design Document

## Overview

This design describes a `docs/` folder that serves a dual purpose: human-readable project documentation and machine-consumable AI training/context data for the **SoulYatri Speech** project. The folder is generated by hand-authoring content that is grounded in the actual source files under `server/`, and then committed and pushed to a new Git branch on the `origin` remote.

The design intentionally treats documentation as **data**: every prose document under `docs/code/` has a corresponding set of structured training records under `docs/training/`. The structured records (JSONL) are the canonical artifact a fine-tuning or RAG pipeline ingests; the Markdown is the human mirror and the grounding source.

### Goals
- Produce accurate, source-grounded documentation of the SoulYatri Speech architecture, modules, API/protocol, and configuration.
- Produce curated Q&A training data in a documented, machine-parseable JSONL schema.
- Keep the docs decoupled from application code (no changes to `server/`, `client/`, `scripts/`).
- Commit and push to a new branch so a PR can be opened, with no secrets included.

### Non-Goals
- No fine-tuning/training pipeline execution, no hosting, no embedding/vector store build.
- No modification of application source code or runtime behavior.

## Architecture

### Folder Layout

```
docs/
├── README.md                     # Purpose, structure, how to use as AI training context
├── FORMATS.md                    # Format conventions + JSONL schema definition
├── code/
│   ├── index.md                  # Lists code docs + source-file provenance
│   ├── architecture.md           # End-to-end pipeline + Phase 2 components
│   ├── module-reference.md       # server/pipeline/* and server/utils/* reference
│   ├── api-protocol.md           # REST endpoints + WebSocket protocol
│   └── configuration.md          # Settings groups + env var prefixes
└── training/
    ├── index.md                  # Lists training files + schema pointer
    ├── qa.jsonl                  # Canonical curated Q&A (one JSON object per line)
    ├── qa.md                     # Human-readable mirror of qa.jsonl
    └── examples.jsonl            # Worked end-to-end examples (instruction/response)
```

### Content Generation Flow

```
Source files (server/**)  ──read──►  Author code docs (docs/code/*.md)
                                            │
                                            ├─ derive ─►  Curated Q&A (docs/training/qa.jsonl + qa.md)
                                            └─ derive ─►  Worked examples (docs/training/examples.jsonl)
                                            │
                                   validate JSONL (every line parses)
                                            │
                                   git add docs/ + .kiro/specs/
                                   git commit -m "..."
                                   git push -u origin docs/ai-training-context
                                            │
                                   report branch + remote for PR
```

The documentation is grounded in these source files (recorded in `docs/code/index.md` for provenance):

| Doc | Primary source files |
|-----|----------------------|
| architecture.md | `server/main.py`, `server/agent.py`, `README.md` |
| module-reference.md | `server/pipeline/*.py`, `server/utils/*.py` |
| api-protocol.md | `server/main.py` (REST + `/ws/audio/{session_id}`) |
| configuration.md | `server/config.py`, `.env.example` |

## Components and Interfaces

### 1. `docs/README.md`
Top-level index. Describes the folder purpose, the `code/` vs `training/` split, how an AI pipeline should consume the content (read JSONL from `training/`, use Markdown in `code/` as grounding), and a provenance note that content derives from `server/**`.

### 2. `docs/FORMATS.md`
Defines format conventions and the canonical JSONL schema so any consumer can parse the data without guesswork.

**Q&A record schema (`qa.jsonl`):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | yes | Stable unique identifier (e.g., `qa-arch-001`) |
| `question` | string | yes | Natural-language question about the project |
| `answer` | string | yes | Accurate answer grounded in the code docs |
| `tags` | string[] | no | Topic tags (e.g., `["architecture","vad"]`) |
| `source` | string | no | Doc section or source file the answer is grounded in |

**Example record:**
```json
{"id":"qa-arch-001","question":"What is the end-to-end voice pipeline in SoulYatri Speech?","answer":"Audio is captured in the browser and sent over WebRTC/WebSocket to the FastAPI server, which runs VAD (Silero) to detect speech segments, STT (faster-whisper) to transcribe, an LLM (Ollama) to generate a reply, and TTS (edge-tts) to synthesize audio that is streamed back.","tags":["architecture","pipeline"],"source":"docs/code/architecture.md"}
```

**Worked-example record schema (`examples.jsonl`):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | yes | Stable unique identifier (e.g., `ex-001`) |
| `instruction` | string | yes | A task/prompt (e.g., "Start the server") |
| `response` | string | yes | The correct walkthrough/answer |
| `tags` | string[] | no | Topic tags |

Conventions documented in `FORMATS.md`:
- Markdown for prose (`.md`), JSONL for structured data (`.jsonl`).
- JSONL: exactly one JSON object per line, UTF-8, no trailing commas, no comments.
- Every JSONL line must independently `json.loads()` without error.

### 3. `docs/code/*` — Code Documentation

**architecture.md** documents:
- The Phase 1 baseline pipeline: `Audio → WebRTC → VAD → STT → LLM → TTS → Audio`.
- The Phase 2 `VoiceAgent` orchestration: turn state machine, filler routing (`filler_only` / `filler_then_pipeline` / `pipeline_only`), parallel emotion+speaker feature extraction, and barge-in handling.
- Component-to-technology mapping (Silero VAD, faster-whisper, Ollama Qwen3, edge-tts).

**module-reference.md** documents each module's responsibility and key public types/methods (names taken directly from source):
- `pipeline/vad.py`: `SileroVAD`, `VADConfig`, `SpeechSegment`; `load_model`, `process_audio`, `process_frame`, `reset`.
- `pipeline/stt.py`: `WhisperSTT`, `TranscriptionResult`; `load_model`, `transcribe`, `transcribe_bytes`.
- `pipeline/llm.py`: `OllamaLLM`, `LLMResponse`, `SOULYATRI_SYSTEM_PROMPT`; `initialize`, `generate`, `generate_stream`, `close`.
- `pipeline/tts.py`: `EdgeTTS`, `TTSResult`; `synthesize`, `synthesize_stream`, `detect_language`.
- `pipeline/session.py`: `SessionManager`, `SessionState`, `ConversationTurn`; `get_or_create_session`, `add_turn`, `get_llm_history`.
- `pipeline/turn_state.py`: `TurnStateMachine`, `TurnState`, `TurnEvent`, `VALID_TRANSITIONS`, `STATE_TIMEOUTS`.
- `pipeline/filler.py`: `FillerPhraseBank`, `FillerRouter`, `FillerPhrase`, `RoutingDecision`.
- `pipeline/features.py`: `FeatureExtractor`, `TurnMetadata`.
- `pipeline/emotion.py`: `EmotionExtractor`, `EmotionResult`, VAD dimensions.
- `pipeline/speaker.py`: `SpeakerEncoder`, `SpeakerEmbedding`; cosine similarity / `is_same_speaker`.
- `pipeline/barge_in.py`: `BargeInDetector`, `BargeInEvent`.
- `utils/audio.py`: PCM/float conversion, resample, WAV helpers, sample-rate constants.
- `utils/metrics.py`: Prometheus metrics with the `soulyatri_` prefix.
- `utils/logging_config.py`: structlog setup, `get_logger`.

**api-protocol.md** documents:
- `GET /health` → `{"status","version","phase"}`.
- `GET /metrics` → Prometheus text exposition.
- `GET /api/token?room=&identity=` → LiveKit token JSON (`token`, `url`, `room`, `identity`).
- `WS /ws/audio/{session_id}`: binary frames carry 16-bit PCM (client→server at 16kHz, server→client at 24kHz); text frames carry JSON control (`{"type":"config","sample_rate":16000}`, `{"type":"end"}`) and server events (`transcript`, `audio_meta`, `turn_metadata`).

**configuration.md** documents the settings groups in `server/config.py` and their env prefixes: root (`SERVER_`/`LOG_`), `LIVEKIT_`, `OLLAMA_`, `WHISPER_`, `TTS_`, `SESSION_`, `EMOTION_`, `SPEAKER_`, `FILLER_`, `BARGE_IN_`, cross-referenced with `.env.example`.

### 4. `docs/training/*` — Curated Training Data
- `qa.jsonl`: 20+ curated Q&A records spanning setup, architecture, configuration, protocol, and modules. Each `answer` is consistent with `docs/code/*`.
- `qa.md`: human-readable mirror grouped by topic.
- `examples.jsonl`: at least 3 worked examples (e.g., quick-start sequence, generating a LiveKit token via `/api/token`, the WebSocket audio handshake).

## Data Models

The two JSONL schemas defined above (Q&A record and worked-example record) are the only structured data models. They are deliberately simple, flat objects so they map cleanly onto common instruction-tuning formats (`instruction`/`response`) and RAG ingestion (`question`/`answer` + `source`).

## Error Handling

This feature produces static content and Git operations; runtime error handling is minimal but the process guards against these failure modes:

- **Inaccurate content (drift):** Mitigated by grounding every doc in named source files and recording provenance in `index.md`. Each Q&A `source` points back to a doc section/file.
- **Malformed JSONL:** Before commit, validate that every line of each `.jsonl` file parses as a standalone JSON object (e.g., `python -c` reading each line). A failure blocks the commit until fixed.
- **Accidental inclusion of unrelated/secret files:** Stage only `docs/` and `.kiro/specs/` explicitly (no `git add .`). Never stage `.env` or credentials. Verify staged file list before committing.
- **Pushing to a protected branch:** Never push to `main`. Create and push to a new branch `docs/ai-training-context` with upstream tracking, then report the branch + remote URL for PR creation.

## Testing Strategy

Validation focuses on correctness of the data artifacts rather than application behavior:

1. **JSONL validity check:** A script iterates every line of `qa.jsonl` and `examples.jsonl` and asserts each parses as JSON and contains the required schema fields (`id`, plus `question`/`answer` or `instruction`/`response`). This satisfies Requirements 4.3, 4.4, and 6.3.
2. **Schema/ID checks:** Assert `id` values are unique within each file and required fields are non-empty.
3. **Cross-consistency spot check:** Manually verify a sample of Q&A answers against the corresponding `docs/code/*` sections and source files (Requirements 2.5, 3.4).
4. **Provenance check:** Confirm `docs/code/index.md` lists the source files each document derives from (Requirement 6.1).
5. **Git pre-push verification:** Confirm the staged file list contains only `docs/**` and `.kiro/specs/**`, and that no `.env`/secret files are included (Requirements 5.1, 5.3, 5.4).

A small, self-contained validator script (run once before commit, then removed if it is a throwaway, or kept under `docs/` if useful) will perform checks 1–2. No application test framework changes are required.
